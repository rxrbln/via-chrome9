# Wine closed-key shader differentials

This tranche makes the next fragment-runtime classes reproducible across the
Windows compiler, the Linux compiler/configuration pass, and the Xorg fixed
builders.  The machine-readable rows are in
[windows-closed-key-shader-corpus.tsv](windows-closed-key-shader-corpus.tsv).
They are compiler evidence and bounded closed objects, not permission to
accept arbitrary native instructions from userspace.

## Reproduction and provenance

The PE32 probe is `tools/wine_shader_probe.c`, built with the documented
no-timestamp command.  The executed wrapper SHA-256 was
`a87f9bf57008362bdfb8e616860b19dd8d8442d17b5c5f0e77edb4b2ec13d94c`;
the Direct3D UMD SHA-256 was
`8ac6959fc3ab21b73fcf37ae4615e87ab285f3a56bc27623f3094d82cee49b45`.
Each row's token payload was wrapped by `ffff0200` and `0000ffff` with
`tools/d3d_shader_blob.py`, then passed through tokenizer `0x101dbd30`,
dispatcher `0x101dca80`, and finalizer `0x10203530`.  Raw and finalized stores
were identical for all rows in this bounded set.

The OpenGL ICD SHA-256 is
`a54e38ca7c038d7ce4937f9d940aa6e7d02886ef097730f4a1ae03979c9b4d2c`.
Static byte matching maps the D3D tokenizer to OGL RVA `0x244530`, compiler
constructor to `0x2463c0`, and finalizer to `0x256550`; the selected PS
dispatcher has the corresponding OGL body at `0x245280`.  A temporary OGL
wrapper could not pass `LoadLibraryA` in the headless Wine environment and
returned probe status 10, so the corpus does not falsely label OGL output as
dynamically executed.  The byte-matched backend and the OGL upload path remain
an independent static cross-check; the D3D rows are the dynamic Windows
evidence.

## What the differentials prove

ALU-only `v0*c0`, `c0*c1`, and both constant-alpha orientations match the
Linux configuration-two words exactly.  Swizzle `e4` to `ff` changes
`30081053/00f08005` into either `300816db/00f08005` or
`b0081053/00f0806d`.  Replicated alpha therefore changes the split high
modifier as well as the low 12-bit swizzle; changing only `053` to `6db` is
not a general encoder.

The probe's deliberately minimal allocation callback returns zero for every
temporary.  One- and two-texture Windows rows are consequently semantic
differentials: TAUs are `201001b0` and `211111b1`, and sampled sources alias
virtual zero.  The Linux compiler/configuration pass supplies the executable
physical allocation and controls recorded in the TSV.  This is why Windows
`tex0*c0` is not copied directly into a command stream even though its opcode,
constant source, and identity swizzles are useful cross-checks.

The Windows direct-output optimization drops alpha swizzles attached to a
sample temporary.  `tex0*tex1`, `tex0*tex1.aaaa`, and
`tex0.aaaa*tex1` all finalize to the same ALU and TAUs; the same loss appears
for `tex0.aaaa*c0`.  This negative result is a validation rule: these keys
must never be generated by editing the generic Windows result.

## Exact two-texture alpha closure

The proprietary Xorg binary closes both orientations with unmodified fixed
builders.  `Modulate_H5_via_mask2` at `via_drv.so:0x32c50` emits

```text
0140b6d0 302026db 00f20005 0000007f   # r1 = r0 * r2.wwww
01c00000 301c0000 00f20105 000d083f   # oC0 = r1
```

An isolated call to `Modulate_H5_src_comp_Aa_Ca2` at `0x33290` with mode 5
emits the complementary form

```text
0140b6d0 b0202053 00f2006d 0000007f   # r1 = r0.wwww * r2
01c00000 301c0000 00f20105 000d083f   # oC0 = r1
```

Both complete 40-dword helper packets use:

```text
A90..A9a 90018000 91000003 92020002 93000002
          94000000 95000000 96000000 97000000
          98000000 99000000 9a000000
TAU       301001b0 311211b1
```

Mode 6 of `src_comp_Aa_Ca2` emits full `r0*r2` with first ALU
`0140b6d0 30202053 00f20005 0000007f`.  This corrects the old `30202013`
transcription and independently promotes the full-RGBA fixed packet from a
field-derived candidate to an exact vendor object.

## Runtime key and verifier contract

The current key enum needs one additional logical leaf,
`CHROME9_FS_LEAF_TEX1_A`, to represent the right-alpha object without
confusing sampler identity.  Admit exactly these ordered expressions:

```text
MUL(TEX0,   TEX1_A) -> via_mask2 object
MUL(TEX0_A, TEX1)   -> src_comp mode-5 object
```

Do not commute an alpha-decorated texture leaf.  Each key requires
`constant_mask=0`, `varying_mask=0`, `sampler_mask=3`, `tau_count=2`, and
`alu_count=2`; exact controls, both TAUs, both ALUs, and zero slack are part
of the equality check.  The sampler/image/FVF closure is the existing
two-texture object: samples land in physical `r0` and `r2`, and the output
temporary is physical `r1`.  A one-ALU generic object is invalid for either
alpha key even when its decoded multiply appears plausible.

The safest silicon vectors use poison RGB in the alpha-supplying texture.
For `TEX0*TEX1_A`, set texture 0 to `(0.8,0.4,0.2,0.6)` and texture 1 to
`(1,0,1,0.25)`; expect approximately `(0.2,0.1,0.05,0.15)`, not the magenta
full-vector product.  For `TEX0_A*TEX1`, retain distinct texture-0 RGB with
alpha `0.25`, set texture 1 to `(0.2,0.4,0.8,0.6)`, and expect
`(0.05,0.1,0.2,0.15)`.  Run `full -> alpha -> full` with unchanged BOs,
nearest/clamp sampling, both source/target guards, and texture invalidation;
this catches stale A90/TAU mapping as well as the swizzle itself.

For the remaining keys, validation is the row's ordered logical key plus the
exact instruction/control/resource tuple.  RGBX additionally requires the
driver-owned `c0.x=0x3f800000`; user uniforms may not alias that slot.  Until
these vectors pass, the newly recovered objects remain offline-only and do
not justify advertising broader GLSL or arbitrary native-program support.
