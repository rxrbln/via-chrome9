# Chrome9 cmd19 floating-point boundary and silicon oracle

## Result

The Chrome9 Linux and Windows PS 2.0 compilers do not validate, canonicalize,
or specialize shader code for constant values.  Both accepted D3D `DEF c0`
payloads containing signed zero, subnormals, the finite endpoints, infinity,
quiet NaN, and signaling NaN.  They emitted the same finalized one-record
objects for every value:

```text
MOV oC0,c0       01c00530 301c0053 00f08005 000d0820
MUL oC0,v0,c0    0140b6d0 30080053 00f04005 00000820
A90..A9b         90058000 91000000 92000001 93000000
                  94000000 95000000 96000000 97000000
                  98000000 99000000 9a000000 9b000000
```

The machine-readable inputs and results are in
[chrome9-cmd19-fp-compiler-corpus.tsv](chrome9-cmd19-fp-compiler-corpus.tsv).
This proves value-independent compilation, not arithmetic behavior.  In
particular, the compiler accepting NaN or infinity is not a safety result.
The cmd19 exponent-`ff` rejection remains the only demonstrated barrier
between those values and the GPU.

PS 2.0 runtime constant upload is likewise bit-preserving.  The Linux 5.75
path copies user constant dwords under selector `22030000`; the matching
Windows D3D and OpenGL paths do the same.  The legacy PS 1.x C1 conversion is
a separate path and must never be applied to cmd19.

## Exact input domains

Cmd19 has two very different sources:

* `c0` carries four arbitrary binary32 dwords, subject today only to the
  exponent-`ff` finite check.
* `v0` comes from packed D1 color.  It is nonnegative, finite, and bounded by
  one; it cannot transport a floating-point signed zero, subnormal, NaN, or
  infinity bit pattern.

Consequently `MOV v0` has no binary32 edge-value surface.  For accepted
`MUL v0,c0` or `MUL c0,v0`, the product magnitude cannot exceed the finite
constant magnitude.  With finite c0, no infinity or NaN can be generated by
the multiply.  The two operand orders have distinct, compiler-exact A/C
encodings and must be tested independently, but their finite numerical
result should agree.

The current finite test admits these important boundaries:

| class | positive | negative | current policy |
|---|---:|---:|---|
| zero | `00000000` | `80000000` | accept |
| minimum subnormal | `00000001` | `80000001` | accept under default mode |
| maximum subnormal | `007fffff` | `807fffff` | accept under default mode |
| minimum normal | `00800000` | `80800000` | accept |
| maximum finite | `7f7fffff` | `ff7fffff` | accept |
| infinity | `7f800000` | `ff800000` | reject before packet construction |
| quiet NaN sample | `7fc00001` | `ffc00001` | reject before packet construction |
| signaling NaN sample | `7f800001` | `ff800001` | reject before packet construction |

There is no static evidence that a finite endpoint needs a tighter safety
gate.  Subnormal acceptance is semantically safe only for the default shader
floating-point mode until the fixed hardware behavior is measured.

## Bounded silicon oracle

Use one guarded BGRA8888 target, D16, the existing perspective-correct vertex
record, COPY blend, full color mask, and the byte-exact MOV/MUL objects above.
Every row is `known-good -> candidate -> known-good`; verify target/depth
guards, fence retirement, command error state, and reset counters after each
draw.  Change only c0 or the ordered source tuple.  Do not introduce raw
packets or a new ioctl.

1. **Host rejection first.** Submit both infinities, both sample NaNs, and
   each sign.  Require `-EINVAL` before reservation/publication, no fence or
   submission counter advance, an unchanged target, and a succeeding
   ordinary draw.  The proprietary compilers do not provide this protection.
2. **Finite endpoint safety.** With alpha test disabled, run MOV c0 for both
   zeros, both minimum and maximum subnormals, both minimum normals, and both
   maximum finite values.  Expected BGRA results are black for zeros,
   subnormals, and negative values, and saturated white for positive maximum
   finite.  This is a hang/state-safety gate, not proof of the internal float.
3. **Denormal discriminator.** Clear to opaque green.  Emit MOV c0 with RGB
   `(1,0,0)` and alpha `00000001`, then `007fffff`, under fixed alpha test
   GREATER/reference zero (`A33=33004000`).  A preserved positive subnormal
   passes and writes the red candidate; FTZ kills it and leaves green.  Repeat
   each value with MUL, v0 alpha `ff`, and the same c0 alpha.  Ordinary BGRA8
   readback alone is insufficient because both preserved and flushed alpha
   quantize to byte zero.
4. **Signed-zero limit.** Repeat the alpha oracle with `+0` and `-0`; both
   must compare equal to zero and be killed.  This verifies safe comparison
   behavior but cannot prove preservation of the sign bit.  Closing signed
   zero itself needs a chained sign-sensitive operation such as RCP/CMP or a
   float render target, neither of which belongs in cmd19 v1.
5. **Operand order.** For identity swizzles, compare `v0*c0` with `c0*v0`
   using c0 `(0.5, 1.0, 2.0, -1.0)` and primary bytes
   `(01,40,80,ff)`, then the finite boundary vectors.  Require identical
   pixels and closure while retaining each order's exact compiler record.
6. **Rounding discriminator.** First bracket one A33 reference threshold
   with adjacent positive binary32 MOV constants.  Offline exact-rational
   search then chooses a primary byte `m` and c0 so multiplication by the
   unpacked `m/255` rounds to opposite adjacent floats under RTE and RTZ,
   straddling that measured threshold.  Run both operand orders.  A mere
   one-byte tolerance does not identify the arithmetic rounding mode.

Do not submit NaN/Inf through a temporary debug escape on the primary
machine.  If exceptional arithmetic is later required, use a separately
guarded opt-in kernel build and make reset recovery part of every vector.

## NIR admission policy

Per-instruction `nir_alu_instr::fp_math_ctrl` and shader-wide
`float_controls_execution_mode` are separate contracts.

For the current one-record, terminal BGRA8 cmd19 subset, no
`fp_math_ctrl` bit by itself requires rejection:

| NIR control | reason it is closed for cmd19 v1 |
|---|---|
| preserve signed zero | direct emission performs no transform; normalized color storage and fixed comparisons cannot distinguish the sign of zero |
| preserve infinity / NaN | finite c0 plus bounded finite v0 cannot present or generate either class |
| no contract | there is only one operation and no contraction opportunity |
| no reassociation | there is only one operation; retain the original A/C operand order |
| no transform / exact | the backend emits the selected operation directly, with no algebraic replacement |

That conclusion is deliberately limited to a terminal one-record shader and
normalized render target.  A temporary consumer, RCP/RSQ, MIN/MAX/CMP,
floating render target, or exceptional-value widening makes the preservation
bits observable and requires new numerical gates.

Shader-wide FP32 execution modes do require a fail-closed check because no
programmable hardware mode has been recovered:

| FP32 execution mode | cmd19 policy before silicon characterization |
|---|---|
| default (`0`) | allow |
| denorm preserve | reject |
| denorm flush-to-zero | reject |
| round-to-nearest-even | reject for MUL |
| round-toward-zero | reject for MUL |

FP16/FP64 mode bits are irrelevant only because the classifier already
requires every consumed value and ALU result to be 32-bit.  Contradictory
mode pairs remain invalid.  After the oracle identifies the fixed denormal
and rounding modes, admit only the matching explicit FP32 request unless a
real mode-control field is independently recovered.  MOV can ignore an
arithmetic rounding request, but keeping one shader-wide gate for v1 is the
safer initial implementation.

This policy does not require tightening the current finite c0 range for
ordinary default-mode GL.  It does require the Mesa cmd19 classifier to read
`nir->info.float_controls_execution_mode`; inspecting only FMUL
`fp_math_ctrl` is not an adequate substitute.
