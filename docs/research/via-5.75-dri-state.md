# VIA 5.75.32.87a userspace 2D/3D state extraction

This note records hardware-facing facts recovered from the symbol-rich 32-bit
Linux binaries in `binary/5.75.32.87a-u910-55689/bin`.  It complements
`via-5.75-kmd.md`: the KMD source defines the privileged memory/submission ABI,
while these two binaries expose the actual state, draw, copy, and synchronization
packets generated by VIA userspace.

The analyzed files are:

| file | build ID | SHA-256 |
|---|---|---|
| `via_chrome9_dri.so` | `f140f76cfb18e3f368245054629d1ef2e67be129` | `fddb4dea85319c76cac3354e43aa9bcb12a8b7f178cee0f70f6c7efe14a69af4` |
| `via_drv.so` | `2652605384b383d1377e040b8f8173b856e9a067` | `5532461314330eda79d13a49145c935d6f12e563219a766ab3b827602d47d787` |

Addresses below are ELF virtual addresses from these exact files.  They are not
runtime addresses after ASLR.  `via_drv.so` has useful global symbols throughout.
`via_chrome9_dri.so` is not stripped either, although most useful DWARF covers
only VIA's software vertex-shader compiler rather than the hardware layer.

## High-value conclusions

- VX900 (`1106:7122`) uses the Xorg driver's **H6 initialization with H5
  destination, texture, pixel-shader, and quad emitters plus an H6 vertex
  shader**.  This dispatch is explicit in `viaInit3DState_H6` at `0x2ff50`.
- A destination is programmed through H2/type `00010000` as `50/51/52`
  parameter words.  Its base is in 256-byte units and pitch in 32-byte units.
- A rectangle draw is an H2/type `00000000` stream of four vertices.  Each
  vertex begins with six dwords (`x`, `y`, `z`, `w`, diffuse, specular), followed
  by two floats per active texture.
- An early harness capture produced 160 dwords because it omitted the
  generation flag written by `viaExa3DInit`.  Setting `state+0x178=1` produces
  the real 7122/H6 188-dword vector, including H6 FVF/linkage and VS constants.
  It retains two earlier corrections: the second VS instruction contains
  `00384154`, and the quad order is TL/TR/BR/BL.  The corrected stream is now
  silicon-validated; see [vp-stall-analysis.md](vp-stall-analysis.md).
- The XRender path contains a complete native H5 pixel shader for an untextured
  modulated draw and many textured variants.  It is a better initial shader
  corpus than guessing the instruction ISA.
- Xorg's VX900 2D fill and copy vectors are fully recoverable.  It brackets 2D
  use with register `006c = 00400000`, establishing a concrete 2D/3D interaction
  packet.
- The DRI command manager submits ring/AGP work through direct writes to mapped
  BAR1 MMIO.  Hooking DRM ioctls alone cannot capture command buffers.
- Pure format/pitch/tiling helpers can already be executed without hardware via
  `qemu-i386` and the existing i686 T2 rootfs.  Full context creation is possible
  in principle but needs fake DRI1/X and DRM mappings; intercepting
  `cmReleaseSpace` is the much smaller capture boundary.

## MMIO BAR mapping proved by Xorg

`VIAMapMMIO` (`via_drv.so:0x4fbe0`) reads `pci_device.regions[1].base_addr`
at `pci_device + 0x44`, i.e. PCI BAR1 in the 32-bit libpciaccess layout, and
performs these maps:

| BAR1-relative range | length | use in the binary |
|---:|---:|---|
| `000000` | `00d000` | main engine MMIO |
| `200000` | `200000` | 2D host BitBLT aperture |
| `00c000` | `000100` | extra aperture for internal chip classes 2 and 9 |

The mapped main base is exported as `MMIOBase`; `VQStart` is
`MMIOBase + 0x8000`, and a stored secondary pointer is `MMIOBase + 0x200`.
This is independent binary confirmation that engine writes belong to BAR1, and
that BAR1+2 MiB is the host-blit window.  The exact instructions are at
`0x4fc11` (BAR1 base), `0x4fc26` (length `d000`), `0x4fc70` (`+8000`), and
`0x4fca7` (`+200000`, length `200000`).

## Command-buffer manager and submission boundary

### Reservation and release

The Innovation manager entry points are:

| symbol | address | recovered behavior |
|---|---:|---|
| `InitDMAManagerInternal_inv` | `0xb1cb0` | chooses double-buffer AGP, ring AGP, or BCI |
| `cmGetSpace_inv` | `0xb2730` | reserves dwords and returns a CPU pointer |
| `cmReleaseSpace_inv` | `0xb2690` | advances, aligns, and kicks |
| `cmKickoffDMA_inv` | `0xb25e0` | dispatches by manager method |
| `cmKickoffRingAGP_inv` | `0xb0fb0` | updates a running ring pause pointer |
| `cmKickoffDBAGP_inv` | `0xb1310` | programs start/end/pause and triggers |
| `cmKickoffBCI_inv` | `0xb15a0` | interprets H0-H7 and writes MMIO |
| `USER_SPACE_KickoffBCI_inv` | `0xb1d80` | same idea with a verbose software decoder |

The request passed to `cmGetSpace_inv` has this observed prefix:

```c
struct cm_request {
        uint32_t requested_dwords; /* +0x00 */
        uint32_t buffer_class;     /* +0x04 */
        uint32_t *cpu;             /* +0x08, output */
        uint32_t available;        /* +0x0c, output */
};
```

Manager fields used by all paths include current CPU pointer `+0x4034`, end
pointer `+0x4038`, and method `+0x4050`: 2 is double-buffer AGP, 1 is ring AGP,
and the fallback is BCI.  Reservation preserves `0x40` bytes at the buffer end.
Release advances by `requested_dwords * 4`, pads to 16-byte alignment with the
shared null-command pattern, and calls `cmKickoffDMA_inv` only when the current
pointer moved past the last submitted pointer.

### Direct-MMIO kickoff

`cmKickoffDBAGP_inv:0xb1438-0xb1529` polls BAR1+`0400` bit 4 clear, writes
`00100000` to BAR1+`041c`, and streams the following to BAR1+`0420`:

```text
60000000 | (start & 00ffffff)
61000000 | (start >> 24)
62000000 | (end   & 00ffffff)
63000000 | (end   >> 24)
64000000 | (pause & 00ffffff)
65000200 | (pause >> 24)
680a0001
```

Before that, it appends `FE020420,0000041c,00300000,CC000000` and pairs of
`CCCCCCC0,DDD00000` to a 32-byte boundary.  `cmKickoffRingAGP_inv` performs the
same dummy padding and then updates only `64/65` for the already-running ring.
The 1122/5122 branch pads to 128 bytes; 7122 follows this userspace function's
32-byte branch.  The KMD's independent VX900 path uses the more conservative
128-byte rule, so a new kernel driver should retain the KMD/live-tested rule.

`cmKickoffBCI_inv` and `USER_SPACE_KickoffBCI_inv` decode signatures
`FE00` through `FE07`.  H0 writes register/value pairs to the normal MMIO base;
H1 copies payload to MMIO+`200000`; H2 uses the header's 16-bit port; H3/H4 and
the remaining cases implement the other documented packet forms.  This makes
the functions useful packet-oracle code, but calling them with fake MMIO still
requires all polls and side effects to be emulated.

## Lowest-risk 3D completion/status vectors

These packets do not need a color target or shader and are preferable to a draw
as the first proof that H2 reaches the 3D parameter engine.

### H5 engine status update

`hwmUpdateStatus_h5` (`via_chrome9_dri.so:0xac970`) emits this when asked for a
status update:

```text
FE020440 0000043c 00010000 CC000000
1C000000 1D000000 CCCCCCCC CCCCCCCC
```

Its shadow-region initialization path first emits:

```text
FE020420 0000041c 00100000 CC000000
02000000 0300011C CCCCCCCC CCCCCCCC

FE020440 0000043c 00010000 CC000000
21000000 | (gpu_address & 00ffffff)
22000000 | (gpu_address >> 24)
CCCCCCCC
CCCCCCCC
```

The routine pre-fills the selected shadow slot with `ffffffff`.  Seeing it
change is a direct command-completion observation.  Address calculation at
`0xacab4-0xacac3` converts the mapped CPU slot into the GPU-relative address.

### Event/fence write

`hwmSendEvent_inv` (`0xac570`) has an explicit 1122/5122/**7122** branch at
`0xac5ee-0xac60c`.  For shadow base `A`, event-slot index `i`, and 24-bit
counter `C`, let `S = A + 16*i`.  It emits:

```text
FE020420 0000041c 00110000 CC000000
04000000 | (S >> 24)
05000000 | (S & 00ffffff)
06000000 | C
07140000 | ((C & ff000000) >> 16) | (S >> 24)
```

The construction is at `0xac760-0xac7a5`.  The routine also mirrors the event
record into a CPU bookkeeping array.  This is the best recovered starting
point for fence characterization, but the write's cache domain and interrupt
semantics still need live validation.

## VX900/H6 2D packets and 2D/3D synchronization

The exact VX900 helpers are in `via_drv.so`, not the generation-ambiguous
`sfmFill_invM1` path in the DRI binary.

### Solid fill

`viaAccelSolidHelper_H6` (`0x2ab60`) emits an aligned H0 packet with seven
register/value pairs:

```text
FE000000 00000007 00000000 CC000000
00000004  mode
00000014  dst_base >> 3
00000008  (dst_pitch >> 3) << 16
00000010  (y << 16) | (x & ffff)
0000000C  ((height - 1) << 16) | (width - 1)
00000058  foreground_color
00000000  command
```

The exact stores are `0x2abc4-0x2ac6d`.  For a plain source copy fill, the
known command is `f0002001`; `mode` and `command` are prepared by
`viaExaPrepareSolid_H6` (`0x2ba50`).  Width and height are nonzero and encoded
minus one.  Base and pitch units agree with the live fill result.

### Screen-to-screen copy

`viaAccelCopyHelper_H6` (`0x2ae20`) emits eight pairs:

```text
FE000000 00000008 00000000 CC000000
00000004  mode
0000001C  src_base >> 3
00000014  dst_base >> 3
00000008  ((dst_pitch >> 3) << 16) | (src_pitch >> 3)
00000018  (src_y << 16) | (src_x & ffff)
00000010  (dst_y << 16) | (dst_x & ffff)
0000000C  ((height - 1) << 16) | (width - 1)
00000000  command_and_direction
```

Negative X/Y copy direction adjusts the respective source/destination starting
coordinates to the last pixel (`0x2af88-0x2afbc`).  Direction flags are in the
final command word; bit `4000` selects reverse Y and bit `8000` (tested as the
sign of the low word) reverse X.

### Required 2D/3D interaction packet

`Command_CRSync_2D3D` (`0x84c40`) recognizes device 7122 explicitly.  For its
flags argument:

- bit 0 contributes `00400000`;
- bit 1 contributes `00800000`.

It emits:

```text
FE000000 00000001 00000000 CC000000
0000006C  sync_flags
```

Both `viaExaSolid_H6` (`0x2b2e0`) and `viaExaCopy_H6` (`0x2b4c0`) call it with
flags 1 before and after the operation.  This sequence should be preserved
around early mixed 2D/3D tests; omitting it risks testing stale cross-engine
state rather than the packet under investigation.

### Host upload packet

For comparison, DRI function `sfm_2DHWdo_3DTextureBlt_invM1` (`0xe1ae0`)
shows an exact H0 + H1 upload form.  Its H0 setup at `0xe1dbb` is:

```text
FE000000 00000008 00000000 CC000000
00000004 80000000
00000014 dst_base >> 3
00000008 pitch_word
00000048 00000000
00000018 00000000
00000010 position_flags
0000000C ((height - 1) << 16) | (width - 1)
00000000 CC002041
```

It follows with `FE010000, payload_dwords, 0, CC000000`, copies row payload,
then closes with H0 pair `00000048,00000000` at `0xe1f0d`.  This confirms H1's
inline host-data semantics, but the setup is from the older `invM1` path and
must not replace the H6 VX900 register map above.

## VX900/H5 render state

### Generation dispatch

`viaExa3DInit` (`0x27960`) selects `viaInit3DState_H6` for PCI ID `7122`.
That initializer installs these important emitters:

| purpose | function | address |
|---|---|---:|
| destination | `viaSet3DDestination_H5` | `0x2e010` |
| drawing | `viaSet3DDrawing` | `0x2be50` |
| draw flags | `viaSet3DFlags` | `0x2be80` |
| composite/blend operator | `viaSet3DCompositeOperator` | `0x2c2b0` |
| texture | `viaSet3DTexture_H5` | `0x2fbf0` |
| aggregate state | `via3DEmitState_H5` | `0x2eb50` |
| rectangle vertices | `via3DEmitQuad_H5` | `0x2e070` |
| pixel shader | `via3DEmitPixelShader_H5` | `0x33900` |
| vertex shader/FVF | `via3DEmitVetexShader_H6` | `0x30a60` |

Thus “H6” is not a wholly separate packet ISA: VX900 deliberately combines
H5 state/pixel pieces with an H6 vertex-program path.

### Setter-complete normal no-texture path

The earlier aggregate-emitter experiment was useful for packet framing but was
not an executable draw oracle: `via3DEmitState_H5` serializes its object without
constructing it.  Zero-filling that object bypasses the setters used by Xorg and
therefore emits invalid blend/FVF/front-end state.

The following is the actual state construction used by the normal
`viaExaPrepareComposite_H5` path, specialized to `PictOpSrc`, no source or mask
texture, a 128-byte-pitch `x8r8g8b8` target, and a 32 by 32 rectangle.  Function
addresses are for the exact `via_drv.so` identified above:

```c
state->h6_generation = 1;                         /* viaExa3DInit: 0x279f8 */
viaInit3DState_H6(state);                         /* 0x2ff50 */
viaSet3DDestination_H5(state, 0x07fd0000, 128,
                       0x20020888);               /* 0x2e010 */
viaSet3DCompositeOperator(state, 1, 0);           /* 0x2c2b0 */
viaSet3DDrawing(state, 12, 0xffffffff, 0xff, 0xff); /* 0x2be50 */
viaSet3DFlags(state, 0, 0, 1, 1);                 /* 0x2be80 */

via3DEmitState_H5(state, cm, 1);                  /* 0x2eb50 */
via3DEmitClipRect_H5(state, cm, 0, 0, 32, 32);    /* 0x2dc20 */
via3DEmitVetexShader_H6(state, cm);                /* 0x30a60 */
via3DEmitPixelShader_H5(state, cm, 0, 0, 0);      /* 0x33900 */
via3DEmitQuad_H5(state, cm, 0, 0, 0, 0,
                 0, 0, 32, 32);                  /* 0x2e070 */
```

`viaExaComposite_H5:0x298e8-0x29a07` brackets that sequence with
`Command_CRSync_2D3D(cm, 0x7122, 2)` and then flushes.  On VX900 that wrapper is:

```text
FE000000 00000001 00000000 CC000000
0000006C 00800000
```

The next H2 emitter pads the two remaining alignment dwords with `CC000000`.
The same H0 packet is emitted after the vertex stream.  This is distinct from
the `00400000` value used to bracket a 2D operation.

The setters establish these state-object fields.  This table deliberately uses
raw names where semantics are not proved:

| state offset | source | observed packet effect |
|---:|---|---|
| `00`, `0c` | destination/drawing dirty flags | force the destination and common-state H2 groups |
| `20`, `24` | drawing arguments 3 and 4 | low 8 bits of subaddresses `86` and `87` |
| `28` | destination GPU byte address | subaddress `50`, address divided by 256 |
| `2c` | destination pitch in bytes | low bits of `52`, pitch divided by 32 |
| `30` | H5 destination-format code | format bits of `52` |
| `34` | format-derived bytes/bits-per-pixel class | no differential in this no-texture vector; do not program directly |
| `38` | active texture count | selects zero-, one-, or two-texture state, VS, PS, and vertex layouts |
| `3c` | flags argument 4 | bit `0x10` in subaddress `00` (`00000011` versus `00000001`) |
| `40..4c` | composite-operator table | low 24 bits of subaddresses `34..37` |
| `50` | flags argument 2 | no differential in the zero-texture path |
| `54` | flags argument 3 | bit `0x40` in subaddress `01` (`01c01540` versus `01c01500`) |

For `PictOpSrc == 1`, the blend table produces exactly `34=000150`,
`35=000114`, `36=000500`, and `37=000200`.  These are not zero/default blend
words.  Omitting `viaSet3DCompositeOperator` was one of the material defects in
the synthetic-state draw.

This vector is exact for the harness's old H5 branch, but it is **not the 7122
path**.  On silicon it leaves the VP/front end waiting because it combines H5
FVF state with the H6 VS.  Do not submit it and do not splice individual H6
words into it.  The exact corrected 188-dword body, including `05000000`,
type-04 subaddresses `61/62`, H3 VS constants and type-33 integer constants,
is recorded and audited in [vp-stall-analysis.md](vp-stall-analysis.md).
That corrected body has now completed on the live VX900, retired with
`0400=0`, rasterized all 1,024 expected pixels, preserved both guards, and
restored the target.

There is no separate `HE3Fire` word in this H5 immediate path.  The state word
`00000011` and FVF program establish the primitive, and consuming the fourth
six-dword vertex completes the quad.  The old Mesa unichrome explicit-fire
sequence belongs to its older fixed-function packet path and must not be mixed
into this VX900 vector.

This XRender vector uses already transformed screen-space coordinates.  Its
`40..52` H5 state and generated VS perform the XRender position linkage, while
`80..83` provide the integer clip rectangle; it is not a general OpenGL
viewport transform.  The proprietary DRI routine `STM_ViewPort_INV`
(`via_chrome9_dri.so:0x1bab80`) updates a much larger context-dependent state
object, including two packed 12-bit clip banks at offsets `0x200..0x20c` and
shader-dependent viewport fixups.  Those writes have not yet been isolated into
a safe standalone H5 packet vector.

Likewise, the vector above is deliberately depth/stencil disabled.  XRender
does not exercise a Z surface.  The DRI `STM_ZWBEnable_INV`,
`STM_Stencil_INV`, and `STM_RenderTarget_INV` routines prove API-to-state bit
packing, but a normal H5 dispatch capture with a real Z allocation is still
required before their internal state bytes can be identified with emitted H2
subaddresses.  Treat depth/stencil enable, Z address/pitch, clears, and cache
lifetime as unresolved rather than grafting old unichrome register words onto
this H5 vector.

### Render target

`via3DEmitState_H5:0x2ebd5-0x2ec4f` emits:

```text
FE020440 0000043C 00010000 CC000000
50000000 | (dst_gpu_base >> 8)
51000000
52000000 | (((dst_pitch >> 5) | dst_format) & 00ffffff)
```

This proves 256-byte base and 32-byte pitch units.  `dst_format` occupies bits
within the lower 24 bits and comes from the H5 format table below.

The same type `00010000` carries blend state at
`0x2ecb5-0x2ed67`: fixed words `38000000`, `3b000000`, `39000000`, and
`3c000000`, followed by `34/35/36/37 | lower_24_bits(blend state)`.

### Texture stage and sampler

For stage index `s` (the EXA path uses at most two), `via3DEmitState_H5` selects
H2 type `00020000` for stage 0 and `01020000` for stage 1.  The first block at
`0x2edcc-0x2ef01` is:

```text
texture_gpu_base >> 8
18001101                    # or 18001100 from the per-stage flag
20000000 | ((height << 12) | effective_width)
21000001
22000000 | ((ceil_log2(height) << 4) | ceil_log2(effective_width))
30000000 | texture_format
```

Bit 15 of subaddress `22` is added when both dimensions are exact powers of
two.  `effective_width` is the original width when pitch equals the canonical
`align(width * bits_per_pixel, 256) / 8` row (normal 32-byte alignment
padding included); otherwise `viaSet3DTexture_H5:0x2fc57-0x2fc88` derives it as
`pitch / (bits_per_pixel / 8)`.  This corrects an earlier mistaken description
of subaddress `20` as containing a logarithm.  The setter's raw argument map is:

```text
state, stage, gpu_base, pitch, auxiliary,
width, height, PICT_format, address_mode, filter_mode,
sampler_class, per_stage_flag, transform_pointer, repeat_type
```

The complete resource builder, rather than this single-level EXA path, proves
that subtype-10 has only eight address entries per stage (L1--L8) and that both
Linux and Windows cap the directly encoded chain at nine total levels.  Exact
linear allocation rules, table emission, the conservative NPOT policy, and the
unresolved L8-rooted tail are in
[resource-layout-clear-cache.md](resource-layout-clear-cache.md).

The normal composite call at `0x29781-0x29806` supplies address and filter
arguments `2,2`, carries the picture-derived sampler class and repeat type, and
passes the picture transform pointer.  `viaSet3DTexture_H5` rejects a transform
whose two checked fields at `+18/+1c` are nonzero; transformed coordinates are
normally prepared by the surrounding XRender path rather than encoded as a
texture matrix here.

YUY2 (`texture_format == 00300000`) takes a special branch and emits
`30300001`.  A second H2 type is `20020000` for stage 0 and `21020000` for
stage 1:

```text
31100000 | (sampler_word & 00efffff)
32000040 | (((filter << 3) | addressing) & 00ffffbf)
```

The format/address fields are recovered; exact semantic names for every width,
height, filter, and wrap bit still need differential captures.

### Depth/stencil

The proprietary internal surface-format-to-depth conversion is explicit in
`INV_D3DFmt_DDPFToDepth` (`via_chrome9_dri.so:0x1a6d60`):

| internal surface format | hardware depth code |
|---:|---:|
| `101d` | `0` |
| `2032` | `6` |
| `2033` | `6` |
| `203f` | `4` |
| `2040` | `5` |

`STM_Stencil_INV` (`0x1955e0`) enables stencil only for internal format
`2033`; it packs compare/op enumerants as `(api_value - 1) & 7`, uses separate
front/back state blocks at hardware-state offsets `0x8c-0x92` and
`0x94-0x9a`, and preserves full 8-bit stencil masks/reference values.
`STM_FastZClear_INV` (`0x195480`) recognizes `101d`, `2032/2033`, and
`203f/2040`, selects a format-specific clear-bit count, and programs the
enable/count fields at hardware-state bytes `0x9c-0x9d`.

Names for `203f/2040` are not present in the useful DWARF, so they should remain
opaque enum values until correlated with the public manual or a controlled
format capture.  The conversion routines do prove native layouts named
`PF_Z16`, `PF_Z24`, `PF_Z24_STENCIL`, `PF_Z32`, and `PF_S8`; notably the
Z24-to-Z16 converter takes bits 8..23, while Z24+stencil-to-Z16 does the same,
consistent with an 8-bit stencil lane beside 24-bit depth.

## Pixel and vertex program packets

### Minimal untextured H5 pixel shader

`via3DEmitPixelShader_H5` dispatches zero-texture draws to
`Modulate_H5_No_Tex` (`via_drv.so:0x317b0`).  The latter emits H2 type
`00010000` with these 13 dwords:

```text
90058000 91000000 92000001 93000000
94000000 95000000 96000000 97000000
98000000 99000000 9A000000 CCCCCCCC DDDDDDDD
```

It then selects H2 type `20030000` and emits this four-dword 128-bit pixel ALU
instruction at `0x3195c-0x31a39`:

```text
01C00000 301C0000 00F04005 000D083F
```

This is an immediately usable known-good shader vector.  It should be treated
as an opaque instruction until the fields documented in `shader-isa.md` are
fully validated.

The DRI binary also exposes static shader arrays.  For example
`sfmBltNoFilterPSCode_inv` at `0x411bc0`, size `0x3c`, is:

```text
FFFF0200 0200001F 80000000 B0030000
0200001F 90000000 A00F0800 03000042
800F0000 B0E40000 A0E40800 02000001
800F0800 80E40000 0000FFFF
```

This appears to use the older D3D-token-style shader path; do not mix it with
the four-dword H5 instruction without the matching upload wrapper.

### H6 vertex program and FVF

`via3DEmitVetexShader_H6` (`0x30a60`) uploads 128-bit instructions through H2
type `31030000`.  In the normal zero-texture state its exact program is:

```text
00380150 00000000 00000000 0008010F
0008014C 00100150 00384154 0004021F
0008414C 00000000 00000000 0008422F
0008814C 00000000 00000000 0008423F
```

The `00380000` field in the third dword of instruction 1 (zero-based) is
intentional.  Static instructions `0x30c85-0x30c99` explicitly OR `0x38` into
scratch byte `state+0x172`; `0x30c9f-0x30cad` then preserves it while forming
the remaining fields.  A previous `00004154` transcription was incorrect.

After the program it emits H2 type `00040000` and:

```text
60800000 | ((active_texture_count + 3) & 1ff)
```

at `0x310cc-0x3113b`.  `STM_FVFSetting_H5` (`via_chrome9_dri.so:0x1bb930`)
copies the API/D3D FVF words directly from context offsets `0x204/0x208` into
hardware state, and records `(fvf0 >> 8) & 0xf` as the texture-coordinate-set
count.  The large legacy `STM_FVFSetting_INV` at `0x1bce20` handles the older
non-programmable packing.  A new VX900 driver should start with the recovered
H6 pretransformed rectangle layout, not port the older FVF switch wholesale.

### Rectangle vertex stream

`via3DEmitQuad_H5` (`0x2e070`) begins with:

```text
FE020440 0000043C 00000000 CC000000
```

and streams four vertices in this exact order: top-left, top-right,
bottom-right, bottom-left.  Positions are single-precision floats with a
`-0.5` pixel-center bias.  Each vertex is:

```text
float x_minus_half
float y_minus_half
00000000             # z = 0.0
3F800000             # w = 1.0
FFFF0000             # diffuse
FFFF0000             # specular
float s0, float t0    # if texture 0 active
float s1, float t1    # if texture 1 active
```

No separate fire word follows.  H2/type 0 is the vertex-data stream and the
configured FVF/primitive state causes emission when a complete primitive is
assembled.

## Layout and tiling arithmetic

### Linear/tiled pitch

`sfmGetSurfacePitch_inv` (`via_chrome9_dri.so:0xebc70`) takes width, an internal
format whose high byte is bits per pixel, and surface flags.

- The normal linear path returns `align(width * bpp / 8, 32)`, minimum 32.
- If the low 16-bit flag has bit 15 set, the path returns
  `align(width * bpp / 8, 16)`, minimum 16, except internal formats `080e`,
  `080b`, and `0815`, which use 64-byte alignment.
- A separate `00200000` flag path computes `align(16 * ceil(width/8), 32)`,
  consistent with a packed/block layout.

The formula was checked by executing the actual function offline under
`qemu-i386`: width 17 returned `0x20`, `0x40`, and `0x60` for 8/16/32 bpp
linear, and `0x50` for 32 bpp with the low-word tiling flag `8000`.

### Tile offset

`sfmCalculateTileOffset_invi` (`0xdee30`) is standalone and gives the byte
offset for `(x,y,pitch,bpp)`:

```text
tile_width_pixels = (bpp == 8) ? 32 : (bpp == 32) ? 8 : 16
offset = 256 * (ceil(pitch / tile_width_pixels) * floor(y / 8)
                + floor(x / tile_width_pixels))
       + ((tile_width_pixels * (y & 7) + (x % tile_width_pixels)) * bpp / 8)
```

The final `x % tile_width_pixels` term follows from the remainder left by the
`x / tile_width_pixels` division at `0xdee64-0xdee7d`.  Actual function output
for `(17,9,256)` was `0x831`, `0x1122`, and `0x2224` at 8/16/32 bpp.
This describes a 256-byte microtile: 32x8 pixels at 8 bpp, 16x8 at 16 bpp, and
8x8 at 32 bpp.

### Mip layout

`sfmCalcMipOffset_inv` (`0xec2e0`) halves each dimension down to 1 and sums
levels with these rules:

- ordinary row pitch is `align(width * bpp / 8, 32)` and height is aligned to
  8;
- compressed/block formats (`flags & 003000`) align width to four texels,
  convert height to four-row blocks, use half the aligned width times the
  format byte size, and align row bytes to 32;
- flag `00080000` aligns each level size to 256 bytes;
- the special `flags & 003002 == 2` path also aligns each level to 256 bytes.

`sfmCalcTextureSizeAlignment_inv` (`0xebb10`) caches aligned width, height,
depth, byte size, and total size at surface offsets `0x188..0x194`.
`sfmGetSubMipAlignment_inv`, `sfmCalcNP2TilingParams_inv`, and
`sfmCalcTileOffsetFromXYZ_inv` are stubs in this build.  Block width/height/depth
helpers all return 1.  Consequently this binary does **not** contain a hidden
complete NPOT/macrotile algorithm; only the microtile equation above is solid.

## Hardware-free capture feasibility

### What works now

The host can execute the 32-bit binary under QEMU.  A tested invocation uses:

```sh
qemu-i386 \
  -L /srv/t2/build/i786-desktop-26.8.15-desktop-x86-pentium-m-linux/TOOLCHAIN/rootfs \
  ./probe ./binary/5.75.32.87a-u910-55689/bin/via_chrome9_dri.so
```

A tiny `dlopen`/`dlsym` probe successfully called
`sfmCalculateTileOffset_invi` and `sfmGetSurfacePitch_inv`.  Therefore pure
format, conversion, shader-assembly, and layout helpers are dynamically
available without Wine, Windows, or a GPU.  Native 32-bit execution in this
container is blocked by its syscall policy, but QEMU user mode works.

### Recommended command-capture shim

Do not start by emulating every DRM ioctl.  Interpose these exported symbols:

```c
int cmGetSpace(void *ctx, struct cm_request *r);
void cmReleaseSpace(void *ctx, struct cm_request *r);
```

Call the real `cmGetSpace`, remember `r->cpu`, and in the release wrapper dump
`r->requested_dwords` from that pointer **before** calling or suppressing the
real release.  For a hardware-free run, suppress the real release and return
success so no MMIO kickoff occurs.  Calls inside the DRI DSO go through PLT
entries and the object has no `DT_SYMBOLIC`, so ordinary ELF preemption is a
plausible route.  Verify preemption with a one-packet unit before relying on it;
if local binding wins, patch the `cmReleaseSpace@plt` relocation in the loaded
object instead.

To reach normal GL context creation, the shim must additionally provide:

- a fake DRI1/X drawable/context or a small in-process caller of the exported
  hardware helpers;
- successful `drmMap`/`drmUnmap` backed by anonymous RAM for MMIO, framebuffer,
  shadow, and command mappings;
- minimal `drmCommandWrite`, `ioctl`, lock/unlock, and map-handle responses for
  initialization;
- idle values in fake BAR1+`0400` and any polled CR status locations;
- stable fake GPU offsets for resources, because emitted packets store GPU
  addresses even when submission is suppressed.

The DRI DSO directly depends on `libstdc++.so.6`, `libm`, `libpthread`,
`libexpat`, `libdrm`, `libgcc_s`, and `libc`; the i686 T2 rootfs supplies them.
`DbgDumpCMD2File` exists at `0x55867c`, but
`DbgDumpCMD2FileKernelMode` (`0xb32e0`) is a no-op in this build.  It is not a
capture mechanism.  `USER_SPACE_KickoffBCI_inv` contains useful textual packet
decoding, but it also performs actual MMIO writes, so it must only be used with
fully fake mappings.

An Xorg-only alternative is attractive for 2D/XRender: initialize the small
command-buffer object expected by `viaAccelSolidHelper_H6`,
`viaAccelCopyHelper_H6`, and the H5 3D emitters and call them directly.  These
helpers merely append dwords until their flush callback is reached.  It avoids
DRI1 and DRM emulation, at the cost of reconstructing the approximately
`0x24`-byte command-buffer prefix (`base`, current dword, capacity, packet type,
flush callback) and the EXA state objects.

## Actionable bring-up order

1. Keep the already validated KMD SF ring/page-table sequence and BAR1-only
   writes.
2. Submit the `hwmUpdateStatus_h5` shadow bind and status update.  Confirm the
   sentinel changes, with bounded polls and reset recovery available.
3. Run Xorg's H6 2D initialization, bracket a fill with the `006c=00400000`
   synchronization packets, and repeat the known H6 solid fill.
4. Program one linear `x8r8g8b8`/`a8r8g8b8` destination through `50/51/52`.
5. Upload the recovered no-texture pixel shader and H6 vertex shader/FVF,
   stream a four-vertex untextured quad, then fence through `hwmSendEvent_inv`.
6. Add the exact single-linear-texture capture in
   [xorg-one-texture-oracle.md](xorg-one-texture-oracle.md); it is the complete
   232-dword normal Xorg path with no mipmaps.
7. Add depth without stencil, then `2033` stencil, then clears.  Keep fast-Z,
   compression, and tiled render targets disabled until plain linear depth is
   repeatable.
8. Validate the 256-byte microtile equation with upload/readback before exposing
   tiled BO modifiers or mipmapped tiled textures.

Every step should use a fresh fence/status slot and time-bounded waits.  A
packet dump from the offline shim should be compared dword-for-dword with the
new Mesa emitter before the vector is tried on real hardware.

## Still missing for a full 3D driver

This binary closes major state/format/packet gaps, but it does not by itself
make a complete Gallium driver possible.  Remaining blockers are:

- validated shader instruction semantics, control flow, register allocation,
  interpolation, texture instructions, and limits for a NIR backend;
- exact primitive/topology, index-buffer, vertex-stream, and instancing fields
  beyond the recovered immediate rectangle path;
- complete depth-format names and depth/stencil clear encoding, MSAA layouts,
  compression metadata, and fast-Z/coarse-Z lifetime rules;
- macrotile/bank-swizzle rules, modifier negotiation, all compressed texture
  layouts, cube/3D textures, and every mip-tail case;
- cache flush/invalidate requirements among 2D, 3D, CR, CPU, SF, and SL;
- production fences, interrupts, context isolation, preemption, hang detection,
  and reset;
- verified resource-location/address bits in every state group and relocations
  for more than one memory domain;
- limits and interactions for MRT, blending, sRGB, color masks, queries, and
  conditional rendering;
- a security verifier that checks packet lengths, address ranges, forbidden
  MMIO, shader uploads, and cross-buffer branches.

The practical implication is that the recovered status, H6 2D, linear render
target, known shader, and immediate quad vectors are sufficient for staged 3D
execution experiments now.  They are not sufficient to expose unrestricted
OpenGL until address validation, reset, and shader correctness are in place.
