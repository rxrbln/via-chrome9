# Chrome9 texture-environment combine contract

Status: exact Mesa semantics, compiler-exact Chrome9 programs, and bounded
silicon oracles.  Existing one-texture REPLACE/MODULATE and two-texture
full-RGBA MODULATE objects are live on VX900.  The newly recovered ADD,
missing-alpha REPLACE, and mixed-stage programs have not run on silicon and
must remain behind distinct capability bits until their guarded tests pass.

**Two-texture provenance correction.**  Any multi-ALU Linux object below
whose controls begin `90000000` and whose TAUs begin `a010...` was reproduced
with the historical swapped validator/processor callbacks.  Such bytes remain
complete fixed-program candidates, but are not generic production compiler
output.  Production objects must be regenerated as in
[`chrome9-production-four-alu-provenance.md`](chrome9-production-four-alu-provenance.md).

This note covers the fixed-function texture-environment subset needed around
the ioquake3 GL1 path.  It deliberately separates API channel semantics from
native storage channels.  In particular, classic `GL_ADD` is not generally a
four-component ADD.

## Evidence and reproduction

`main/texstate.c:51..61,145..284`.  `calculate_derived_texenv()` starts with
`TEXTURE,PREVIOUS` for both RGB and alpha, changes the missing-channel source

alpha MODULATE, except that INTENSITY adds alpha.  The generic fixed-function

## Exact classic texture-environment equations

Let `P` be the result entering a unit: primary color at unit zero and the
previous enabled unit's result afterward.  Let `T` be that unit's decoded
sample.  Clamp/saturation is stage-local as required by the fixed-function
program generated by Mesa.

| texture base format | decoded native sample | REPLACE | MODULATE | ADD |
|---|---|---|---|---|
| RGBA, LUMINANCE_ALPHA | `T.rgb,T.a` | `T.rgb,T.a` | `T.rgb*P.rgb,T.a*P.a` | `sat(T.rgb+P.rgb),T.a*P.a` |
| RGB, LUMINANCE, RED/RG | RGB or replicated L, alpha one | `T.rgb,P.a` | `T.rgb*P.rgb,P.a` | `sat(T.rgb+P.rgb),P.a` |
| ALPHA | zero RGB, stored alpha | `P.rgb,T.a` | `P.rgb,T.a*P.a` | `P.rgb,T.a*P.a` |
| INTENSITY | replicated I in RGBA | `T.rgb,T.a` | `T.rgb*P.rgb,T.a*P.a` | `sat(T.rgb+P.rgb),sat(T.a+P.a)` |

The current native decoders are XRGB/RGB565/L8 = RGB/LLL plus alpha one;
ARGB8888/1555/4444/L8A8 = stored RGB/LLL plus stored alpha; and A8 =
`0,0,0,A`.  That storage result does not remove the API base-format rule.
For example, using the live full-RGBA REPLACE program on XRGB incorrectly
forces fragment alpha to one instead of preserving `P.a`.  This may be
invisible in an XRGB target but is visible to alpha test and blending.

Classic GL modes are applied sequentially.  Two MODULATE units therefore
mean `T1 * (T0 * primary)`, not merely `T0*T1`.  The normal ioquake3
base/lightmap fast path also supplies an all-white primary array today, but
the shader key must retain primary because it is a real varying and can
change.  ioquake's captured 2-D XRGB key is
`rgb=T0.rgb*primary.rgb, a=primary.a`; full-RGBA multiplication is exact only
because an XRGB sample has alpha one.

## Exact one-texture native objects

All objects below use the established one-sampler texture/image/FVF state.
The common control/TAU tuple is:

```text
A90..A9a 90018000 91000001 92010002 93000001
          94000000 95000000 96000000 97000000
          98000000 99000000 9a000000
TAU       301001b0
```

### RGBA/LA classic ADD

The exact execution-form ALUs are:

```text
00400550 50140924 00700005 00001820  # sat oC0.xyz = r0.xyz + v0.xyz
0140b6d0 b0040b6b 008200b6 00000820  # oC0.w   = r0.w * v0.w
```

The first instruction is the native ADD/MAD family with a literal-one source,
XYZ write mask, sampled `r0`, and input `v0`.  The second is W-only MUL.
ADD's dword-3 `00001820` includes destination-saturate bit 12.  The otherwise
similar `00000820` object is a useful compiler differential but is not classic
GL texture-environment ADD: Mesa requires stage-local saturation, which also
matters if a later texture stage consumes the result.
The corresponding dynamically executed Windows words before physical
allocation are:

```text
00400550 50140924 00700000 00001820
0140b6d0 80040b6b 008000b6 00000820
```

The Windows shader/ALU/TAU SHA-256 values are respectively
`f3b263fc975f5c471d14091b63e6029e23f7c3a579b28ac4835ffd36d0ac3072`,
`0b6a8508b5d481a0c80839e54da6b80371a4b723b32e5dff697defd6a207c590`,
and `6bc2d9f1a19245224609b68f16f1fede46da85317e0860339a6c34e2d1aa980d`.
This two-ALU program occupies the same fragment-store space as the existing
one-texture MODULATE object; global draw-body length is therefore unchanged
relative to that object.

### RGB/L8 classic ADD and REPLACE

For formats without API alpha, ADD keeps the XYZ instruction above and
replaces the W instruction with primary-alpha MOV:

```text
00400550 50140924 00720005 00001820  # sat oC0.xyz = r0.xyz + v0.xyz
01c00530 b01c0053 008040b6 000d0820  # oC0.w   = v0.w
```

REPLACE changes only the first instruction:

```text
01c00530 501c0053 00720005 000d0820  # oC0.xyz = r0.xyz
01c00530 b01c0053 008040b6 000d0820  # oC0.w   = v0.w
```

Both retain the same controls and TAU.  Windows independently emits the same
operations before dependency rewrite.  Its ADD shader/ALU hashes are
`d9760a2420bfbb793a61322a8edec6a033bf146b44a23a1c3ec3b9108317f0a6` /
`e006a4be46ad443075a39d8ff5441c7802550acfcff8a4beebd1e8d0b8690e82`;
REPLACE is
`bfd731d9fe0471885e4ecf3b4608c77ac9bcba2bd8c5f81844dbed109153d415` /
`c6a1f94034b3dd0a386bba65b2f9d0221a7783cf76a4bc3e8a47bdc510cd30e2`.
Their TAU hash is the one-sampler hash above.

The existing full-vector REPLACE and MODULATE objects remain the preferred
RGBA objects:

```text
# REPLACE: controls have A92=92010001
01c00000 301c0000 00f20105 000d083f  # oC0 = sampled r0

# MODULATE
0140b6d0 30040053 00f20005 0000007f  # r1 = sampled r0 * input v0
01c00000 301c0000 00f20105 000d083f  # oC0 = r1
```

Both have live VX900 coverage.  The `30040053` identity word is exact; the
stale `00040053` transcription is not an execution-form packet word.

ALPHA-only modes need dedicated lane reconstruction: preserve `P.rgb`, write
only sampled/multiplied alpha, and do not expose native A8 REPLACE as an
ordinary four-lane key.  INTENSITY ADD similarly needs ADD in both lane groups
rather than the RGBA alpha-MUL object.  Neither closed object is recovered in
an executable physical schedule here, so both remain fallback cases.

### Full MODULATE and alpha-source forms

The live full-RGBA two-texture object remains:

```text

          98000000 99000000 9a000000
```

## Crossbar and key restrictions

Chrome9 crossbar selection is shader resource routing, not an A30/A31 sampler
mode.  Native TEXLD duplicates the logical sampler id in TAU bits `[27:24]`
and `[3:0]`; s0/s1 appear in the raw words as `201001b0/211001b1`, while the
dependency finalizer rewrites their high bits according to the entire
schedule.  Therefore:

* retain ordered logical leaves `TEX0`, `TEX1`, `TEX0_A`, `TEX1_A`,
  `PRIMARY`, and `PREVIOUS` in the Mesa/kernel key;
* range-check the logical sampler before encoding; never infer s0 from a
  finalized word whose bit 28 could also have come from an invalid s16;
* bind each TEX leaf to its matching image, sampler state, coordinate varying,
  cache invalidation, and BO reference.  Swapping images alone is not a
  crossbar implementation;
* canonicalize only operations which are genuinely commutative and have no
  alpha-decorated operand.  `T0*T1_A` and `T0_A*T1` select different exact
  ALUs;
* permit at most the two proven distinct samples and only the complete closed
  programs above.  Repeated references can reuse one sampled temporary, but
  arbitrary GL combine graphs, three samplers, DOT3, INTERPOLATE, or raw
  user-supplied native instructions remain rejected; and
* advertise `ARB_texture_env_crossbar` only after every advertised source
  selector and unit count is representable.  The closed two-leaf keys alone
  are useful internal lowering but do not justify the general extension.

Old UniChrome `via_texcombine.c` does not handle explicit `GL_TEXTUREi`
sources in its source switches.  Mesa's generic fixed-function compiler does
support them by loading all referenced textures before emitting stages.  This
is further reason to use the resolved NIR/closed-expression key as authority,
not the old driver's extension string or stage number.

## Safe hardware discriminators

Use BGRA8888 target A52=`99`, nearest/clamp sampling, canonical guarded
textures, normalized D1 (`A02=020041d1`), finite positive RHW, complete cache
invalidation, a retirement cookie, and the existing quarantine policy.  Run
each new object as `known live -> new -> known live` without resetting the
context.

1. **RGBA ADD:** D1=`804080c0`, sampled ARGB=`40804020`.  Expect approximately
   `20c0c0e0`: RGB adds, alpha multiplies.  Four-lane ADD instead yields alpha
   near `c0`; four-lane MUL yields dark RGB.
2. **XRGB REPLACE preserving alpha:** D1 alpha=`40`, sample XRGB=`00804020`.
   Expect `40804020`.  The live full-vector REPLACE object incorrectly gives
   `ff804020` for this API semantic, making this a strong lane test.
3. **RGBA MODULATE regression:** use the RGBA ADD operands and expect roughly
   `20202018`.  This must still select the live `30040053` program after an
   ADD draw.
4. **Two-source ADD:** textures `804080c0` and `40804020`; expect
   approximately `20c0c0e0`.  A full-vector ADD produces alpha near `c0`;
   ordinary two-texture MODULATE produces dark RGB.
5. **MODULATE then ADD:** primary=`80808080`, T0=`804080c0`, T1=`40804020`.
   Expect approximately `10a08080`.  Plain `T0*T1`, omitted primary, and
   four-lane final ADD all differ strongly.
6. **Two MODULATE stages:** reuse the live red/black/blue/yellow two-texture
   quadrant vector with primary=`ff808080`; expect half-intensity nonblack
   quadrants.  Ignoring primary returns full intensity.  Then rerun with
   primary alpha `80` into BGRA to prove the alpha product too.

Allow one LSB per normalized multiply and byte conversion, but no tolerance
for wrong lanes.  Verify every source/target guard, command retirement,
`0400` work state, and the full following live draw.  No timeout permits a
nearby program retry.

## Confidence and promotion order

| key | exactness | silicon | action |
|---|---|---|---|
| RGBA REPLACE | Xorg/Linux packet exact | live | keep current |
| RGBA one-texture MODULATE | Xorg/Linux packet exact | live | keep current |
| RGBA two-texture MODULATE | Xorg helper exact | live | keep current |
| RGBA ADD with alpha MUL | Linux execution form + Windows dynamic + Mesa semantic | not run | first new ADD oracle |
| RGB/L8 REPLACE with primary alpha | Linux execution form + Windows dynamic + Mesa semantic | not run | first missing-alpha oracle |
| RGB/L8 ADD with primary alpha | Linux execution form + Windows dynamic + Mesa semantic | not run | after REPLACE |
| two-source ADD with alpha MUL | Linux execution form + Windows dynamic + Mesa semantic | not run | after one-texture ADD |
| MODULATE then ADD | Linux execution form + Windows dynamic + Mesa semantic | not run | after two-source ADD |
| two MODULATE stages plus primary | exact fixed synthesis, both compilers cross-check counts/dependencies | not run | ioquake lightmap priority |
| two-texture alpha-replicate forms | exact Xorg helper objects | not run | after full two-texture regression |
| A8 and INTENSITY lane-special modes | semantic exact, no complete physical object here | none | fallback/reject |
| arbitrary COMBINE/crossbar graph | incomplete | none | reject; do not advertise |

The safest ABI progression is one structured program selector per row, with
the kernel selecting the entire immutable A90/TAU/ALU object.  Never accept
individual opcode, mask, swizzle, count, or transition words from userspace.
Program selection is orthogonal to destination format, blend, alpha test,
depth, mip state, and texture formats; only explicitly enumerated complete
tuples may be combined.
